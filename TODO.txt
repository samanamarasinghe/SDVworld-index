1. THE AUTO-CURATED TAIL -- 1334 ENTRIES, UNREVIEWED
--------------------------------------------------------------------------------

In August 2026 every unvisited repository in the pool was fetched
(harvest/repo_evidence.py, 1455 evidence files under harvest/evidence/) and
curated in one Anthropic batch run (curate/auto_curate.py, Sonnet, ~$10).
1335 records merged into shards 108-119. They are ordinary index entries in
every respect except that no human has read them.

    python3 -c "import json; d=json.load(open('data/sdv-index.json')); \
      print(sum(1 for r in d if (r.get('auto_curated') or {}).get('reviewed') is False))"

What WAS checked, mechanically, over all of them:

  * No entry claims a runs-SDV integration without a code hit outside a
    dependency file. This was the failure mode most feared and it did not occur.
  * No name_collision carries importance != 0; no citation_only carries
    importance >= 4; no `unclear` carries confidence high.
  * Duplicate sweep against the existing index and within the batch: 26 records
    dropped, three retirements applied in shard 120.
  * sdv_component backfilled where an import was missed (shard 121, 66 records).

What was NOT checked:

  * Only 15 entries were read against their evidence by a person. Two of the 15
    were wrong -- both giving a runs-SDV integration to a repository that never
    imports SDV. Expect that error class at roughly one in ten and look for it
    first.
  * Nothing verifies the summaries. The SDV clause at the end of each was
    written from the evidence file, not from the repository.
  * 856 of these entries carry a `needs` string. Most report what the model
    could not SEE -- no README, no call site in the excerpt, no author stated --
    rather than a judgment it could not make.

The honest description of this tier: better than a keyword classifier,
not equivalent to a curator's read. If a decision rests on one of these
entries, open harvest/evidence/<owner>__<repo>.json and check it.

--------------------------------------------------------------------------------
2. WAITING ON THE OWNER
--------------------------------------------------------------------------------

Do not resolve these yourself. Each is recorded twice: as a `needs` string on
the entry, and as a numbered section in docs/open-questions.md carrying the
provisional value already applied. The index is consistent either way; a ruling
either confirms the provisional call or triggers a correction shard.

Two clusters are ripe and would close most of them with one line each:

  (a) wrapper vs modification -- when does building on CTGAN become
      derivative_work rather than api_user? Four cases turn on it.
  (b) the benchmark/comparative-study shape -- when a paper proposes no
      generator of its own, are the generators it runs baselines or evaluation
      subjects? Three cases, judged three different ways.

Also open, and new:

  (c) importance no longer separates significant work from trivial work.
      994 entries sit at 3 and 809 at 4, three quarters of the index in two
      buckets, because the scale measures how central SDV is TO AN ENTRY and in
      a one-purpose student notebook SDV is everything. The convention is being
      applied correctly; the scale is doing less than the default view needs.
  (d) nothing on the page marks the 1334 unreviewed entries. They carry the
      flag; no filter reads it.

To list the ruling-blocked entries from the data:

    python3 -c "import json; d=json.load(open('data/sdv-index.json')); \
      [print(r['id'],'|',r['needs']) for r in d if r.get('needs') and \
      ('convention' in r['needs'].lower() or 'ruling' in r['needs'].lower())]"

    410  confidence: medium  (244 repos, 136 papers, 16 preprints)

  In the papers lane, `medium` almost always means the publisher would not
  serve the full text to an automated fetch, not that the curator was careless.
  Adding a PDF text extractor to the toolchain would move roughly a third of
  every future papers batch from medium to high. There is no pdftotext, fitz,
  pdfminer or PyPDF2 in the default environment; pypdf installs with
  `pip install --break-system-packages`.

     32  scholarly entries have no second source, so the url-vs-DOI
         cross-check in validate.py cannot corroborate their pointer.
      1  code entry is not hosted on GitHub and has no pool row to check.

  Known duplicate questions, both needing a decision then a correction shard:
    - repo-tabularfm-org vs repo-tabularfm: identical titles, org fork vs
      personal account, both vendored_source 4. Test: more commits plus more
      contributors wins; set duplicate_of on the loser.
    - paper-subpopulation-synthetic-ehr-2023 is the arXiv PREPRINT and it is
      the version that survived, while the published JAMIA Open version
      (10.1093/jamiaopen/ooaf091) was never added. This breaks the standing
      rule that the published version is the version of record. The fix is to
      add the JAMIA version and retire the arXiv entry.
    - paper-fingan-crm-banking-2022 (arXiv 2201.11486) has a published twin,
      Neural Computing and Applications 35:6015-6028
      (10.1007/s00521-022-07968-x). Same rule applies. The published PDF has
      been read: its table 9 says LGBM where the preprint entry's evidence says
      xgboost, so fix that line on merge.

  A duplicate class the title sweep does NOT catch: a copy that renamed itself.
  shlomihod/smartnoise-sdk-synth was a copy of the already-indexed
  opendp/smartnoise-sdk under a different title, found only by reading it.

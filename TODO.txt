1. THE AUTO-CURATED TIER -- 3833 ENTRIES, UNREVIEWED
--------------------------------------------------------------------------------

Two batch runs, not one.

The first fetched every unvisited repository in the pool (harvest/repo_evidence.py,
1457 evidence files under harvest/evidence/) and curated it in one Anthropic batch
run (curate/auto_curate.py, Sonnet, ~$10); 1335 records merged into shards 108-119.

The second curated the paper citation tail (curate/paper_curate.py); 2382 records
merged into shards 124-143. Both are ordinary index entries in every respect
except that no human has read them.

    python3 -c "import json; d=json.load(open('data/sdv-index.json')); \
      print(sum(1 for r in d if (r.get('auto_curated') or {}).get('reviewed') is False))"

EVIDENCE QUALITY DIFFERS SHARPLY BETWEEN THE TWO, and the repository half is the
weaker. A repository was judged from an evidence file assembled by a script. A
paper carries evidence_tier, which states what was actually read: full_text,
abstract_context or metadata_only, with confidence capped mechanically by the
tier. 1799 entries now rest on full text, most of them following the August
re-judge in shard 148 -- see section 5's note on that pass.

What WAS checked, mechanically, over the repository half:

  * No entry claims a runs-SDV integration without a code hit outside a
    dependency file. This was the failure mode most feared and it did not occur.
  * No name_collision carries importance != 0; no citation_only carries
    importance >= 4; no `unclear` carries confidence high.
  * Duplicate sweep against the existing index and within the batch: 26 records
    dropped, three retirements applied in shard 120.
  * sdv_component backfilled where an import was missed (shard 121, 66 records).

What was NOT checked:

  * Only 15 repository entries were read against their evidence by a person. Two
    of the 15 were wrong -- both giving a runs-SDV integration to a repository
    that never imports SDV. Expect that error class at roughly one in ten and
    look for it first.
  * Nothing verifies the summaries. The SDV clause at the end of each was
    written from the evidence file, not from the repository.
  * 2667 of these entries carry a `needs` string. Most report what the model
    could not SEE -- no README, no call site in the excerpt, no author stated --
    rather than a judgment it could not make.

The honest description of this tier: better than a keyword classifier,
not equivalent to a curator's read. If a decision rests on one of these
entries, open harvest/evidence/<owner>__<repo>.json and check it -- or, for a
paper, harvest/papers/<slug>.txt if the tier says full_text.

2. WAITING ON THE OWNER
--------------------------------------------------------------------------------

Do not resolve these yourself. Each is recorded twice: as a `needs` string on
the entry, and as a numbered section in docs/open-questions.md carrying the
provisional value already applied. The index is consistent either way; a ruling
either confirms the provisional call or triggers a correction shard.

Two clusters are ripe and would close most of them with one line each:

  (a) wrapper vs modification -- when does building on CTGAN become
      derivative_work rather than api_user? Four cases turn on it.
  (b) the benchmark/comparative-study shape -- when a paper proposes no
      generator of its own, are the generators it runs baselines or evaluation
      subjects? Three cases, judged three different ways.

Also open:

  (c) importance no longer separates significant work from trivial work.
      1626 entries sit at 3 and 1389 at 4, more than three fifths of the index
      in two buckets, because the scale measures how central SDV is TO AN ENTRY
      and in a one-purpose student notebook SDV is everything. The convention is
      being applied correctly; the scale is doing less than the default view
      needs.
  (d) nothing on the page marks the 3833 unreviewed entries. They carry the
      flag; no filter reads it.

Settled since the last revision, recorded here so they are not re-asked:

  * `real_estate` added to the industry vocabulary, and used by one entry.
  * `port` widened. It read "reimplements SDV's design in another language";
    it now covers reimplementation in the authors' own code whatever the
    language, the test being that the design is rebuilt and RUN rather than a
    package invoked. 19 papers in the re-judge turned on this.
  * A retracted work stays in the index with the retraction stated in its
    summary.

To list the ruling-blocked entries from the data:

    python3 -c "import json; d=json.load(open('data/sdv-index.json')); \
      [print(r['id'],'|',r['needs']) for r in d if r.get('needs') and \
      ('convention' in r['needs'].lower() or 'ruling' in r['needs'].lower())]"

7. CLOSED -- DO NOT RESTART THESE
--------------------------------------------------------------------------------

  * Elsevier, all 294 rows. MIT cancelled its entire Elsevier journals contract
    in 2020, so there is no institutional access to articles published 2020 or
    later, and 291 of the 294 are 2020 or later. The TDM API returns 403 on
    entitlement grounds for every DOI including gold open-access ones, and the
    error wording says "authentication", which is misleading -- it is not a key
    or a network problem, and no VPN fixes it. ScienceDirect's own pdfft route
    returns an interstitial whose real link is a bot-challenge solve hop;
    automating that is out of bounds. What remains available is the API's META
    view, which returns title and abstract for every DOI with just a key, if the
    pipeline can use that instead of full text.

  * The self-archive hunt on the login-required works. Confirmed empty five
    ways: Unpaywall, Semantic Scholar openAccessPdf, OpenAlex locations,
    OpenAlex fuzzy title search for sibling preprints, and the arXiv API.
    These are regional engineering journals whose author communities do not
    self-archive. If a NEW closed set appears, run Unpaywall and OpenAlex
    first, then web search the residual -- in that order.

  * Repository discovery. Two full github_tail.py runs a fortnight apart added
    11 repositories between them. The search has converged; another run is not
    worth its rate limit.

  * curate/never-readd.json lists repositories deliberately dropped by a prior
    ruling. Never re-add them, and read that file rather than the built index
    before any bulk pass -- a retired entry is absent from data/sdv-index.json
    while its id and url are still owned by a shard, which is exactly how two
    of them got re-curated in August.

  * The Google Scholar lane, unless a SERPAPI_KEY turns up. Scholar publishes
    no API and its terms forbid automated querying; if it serves a CAPTCHA,
    stop rather than working around it.
